# One gate, not two

Removed the top-level `enabled` config flag added earlier today. Not calling `init()` is how the
devtools are switched off; there is no second way of saying it.

## What changed

- `DevtoolsClientConfig.enabled` deleted, along with the `devtoolsEnabled` local it fed.
- `initCrashCapture(panelAvailable)` now takes its answer from _which call site_ it is: `false` from
  the factory, `true` from `init()`. That already drove the sheet choice; it now drives the tier
  policy and the capture gate too.
- `installCrashHandlers` tracks **per tier** instead of one `installed` flag. The factory installs
  the native tier; a later `init()` has to be able to add the JS tiers on top, and a single flag
  silently refused that.
- `init()` lost its early return and is a straight line again.

## Decisions worth remembering

- **This restores the package's original single-gate philosophy**, which CLAUDE.md describes as
  load-bearing: guard the `.init()` call and that is the whole mechanism. The `enabled` flag was a
  second gate meaning the same thing, and two ways to say one thing is how they drift apart.
- **`enableWhileDevtoolsDisabled` reads better now, not worse.** "The devtools are disabled" meant
  something slightly different from "you didn't call `init()`" while both existed. Now they are the
  same sentence.
- **The upgrade path is the interesting case.** Construct with the flag → native tier only, compact
  sheet. Call `init()` later → JS tiers install, full sheet takes over. There is a test for exactly
  that transition, because the per-tier install guard is the only thing making it work.

## Verification

30 suites / 271 tests. `init-gates.test.ts` was rewritten around the new model — every test that
said `enabled: false` now says "constructed, never inited". `oxlint` / `tsc` clean.
