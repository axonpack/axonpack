Four pieces, all from the package's main entry:

| Piece                | What it does                                                                 |
| -------------------- | ---------------------------------------------------------------------------- |
| `PreviewProvider`    | Holds the config, reads the downloads and the bucket's list, and confirms each start |
| `PreviewList`        | The ready-made screen for QA                                                 |
| `usePreview()`       | The same list and actions, for a screen of your own                          |
| `usePreviewStatus()` | What runs now and the build it runs in, for a banner or badge of your own    |

## The provider

Put it near the root of the app, around everything:

```tsx
import { PreviewProvider } from '@axonpack/preview';
import { previewConfig } from './preview-config';

export default function Root() {
  return (
    <PreviewProvider config={previewConfig}>
      <App />
    </PreviewProvider>
  );
}
```

The config is on [Settings and env files](/docs/preview/environment#the-apps-settings), and every
field is on [Reference](/docs/preview/reference#previewconfig).

<Callout type="warn" title="Mount it on every start">
Once the provider has mounted, it tells the native side that this start worked. The crash fallback
waits for that: a preview that never gets that far is marked broken, and the next start loads the
default bundle. So mount the provider on every start, also in builds where `enabled` is false, and not
behind a login or a lazy screen.
</Callout>

## enabled

`enabled: true` turns previews on. The package does no build-type or store detection: you decide per
build. With `false` the provider never reads the downloads or asks the bucket. The list does not hide
itself, so leave it out of builds where previews are off; `usePreview().enabled` tells you which.

A common setup is an internal build with previews on and a store build with them off, from one env
value:

```ts
enabled: process.env.EXPO_PUBLIC_PREVIEWS === 'on',
```

It applies to debug builds too. A preview chosen in a debug build loads instead of Metro, and the
list says Metro is bypassed. **Use the default bundle** returns to Metro.

## The ready-made list

```tsx
import { PreviewList } from '@axonpack/preview';

export default function PreviewsScreen() {
  return <PreviewList style={{ flex: 1 }} />;
}
```

Put it on a screen QA can reach: a tab in internal builds, a settings row, or a hidden gesture. See
[Show the list anywhere](#show-the-list-anywhere). From the top, it shows:

- **An error snackbar**, only when something went wrong. See [Errors](#errors).
- **The header card:** what runs now, and **Use the default bundle**.
- **Dev preview servers**, in a debug build with that option on.
- **Published previews** for this build.
- **Incompatible:** downloads made for another native build, with **Delete all**.

Pull the list down, or tap the Refresh icon on the header card, to ask the bucket again. A row of
chips that does not fit scrolls sideways.

![The header card for a dev preview server, then the dev preview servers in one grouped card](/preview/screenshots/list-header-servers.png)

### The header card

The title names what runs now: a preview's title, a server's title, **Default** for the Metro the
app starts on when `preview start` gave it no title, or **Built into the app**. A server's address,
such as `localhost:8081`, is under it. Chips say what it is:

| Chip              | When                                                                      |
| ----------------- | ------------------------------------------------------------------------- |
| `Preview`         | A published preview runs                                                  |
| `server: Expo`    | A Metro started with `expo start` or `expo run`                           |
| `server: Preview` | A Metro started with `preview start`                                      |
| `Default bundle`  | Nothing is switched in. This is what the app starts on anyway             |
| `env: <name>`     | The preview was published with `--environment`                            |

A preview also shows who published it and when. **Show details** opens the rest: the branch, the
preview id, the environment, the app's name, version and build, the commit, the platform, what the
build is matched by (app version or fingerprint) and its build key.

When a preview or a picked server runs, **Use the default bundle** restarts on the bundle the app
starts on, and stops using the server. In a debug build a running preview also says that Metro is
not used.

### Errors

When a refresh or an action fails, a snackbar above the header card says what went wrong, in plain
words, and what to try:

| Message                                 | Second line                                                                     |
| --------------------------------------- | ------------------------------------------------------------------------------- |
| Can't reach the bucket at `<host>`.     | On Android, when the bucket is on localhost: use `10.0.2.2`, or run `adb reverse tcp:<port> tcp:<port>` |
| The bucket refused access.              | Check the read key or the bucket's policy.                                      |
| The bucket or the file was not found.   | Check the bucket URL in the preview config.                                     |
| Something went wrong.                   | The error itself                                                                |

**Retry** does again what was tapped last; the first load counts as a refresh. It is left out when
the bucket URL in the config is empty or not a full URL, since asking again can't help. **Dismiss**
hides the snackbar. The raw error also goes to the console. More fixes are on
[Troubleshooting](/docs/preview/troubleshooting).

### Dev preview servers

In a debug build with `devPreviewServers` on, this app's Metro servers are one grouped card. Each row
has the server's title, its address, its branch, and chips:

- **Active:** the app runs from this server now. The row takes the header card's tint.
- **`server: Expo`** or **`server: Preview`:** a plain Expo server, or one started with `preview start`.
- **Default bundle:** the Metro the app starts on with nothing picked. Without a title from
  `preview start` it is called **Default**.
- **Made for another native build** or **Native build unknown:** it may not run on this build.

Tap a row to restart the app on that server. The Active row does nothing. See
[Dev preview servers](/docs/preview/dev-preview-servers).

### Published previews

![Published previews with status and environment chips, changelogs, and Delete, Switch and Update](/preview/screenshots/list-published-previews.png)

Each preview is a card: its title, its branch, chips, the changelog (cut to three lines with **Show
more**), who published it and how long ago, its size, **Delete** and one main action. The one that
runs takes the header card's tint and has an **Active** chip. `env: <name>` shows when it was
published with `--environment`.

| Status chip                | Meaning                                                  | Action     |
| -------------------------- | -------------------------------------------------------- | ---------- |
| `status: not downloaded`   | Published for this build, not on the device              | Download   |
| `status: downloading`      | With a progress bar                                      | None       |
| `status: downloaded`       | On the device and up to date                             | Switch     |
| `status: update available` | Published again since it was downloaded                  | Update     |
| `status: unpublished`      | Still on the device, but no longer in the bucket         | Switch     |
| `status: broken`           | It stopped while starting. A line under it says the default bundle loaded instead | Switch |

The one that runs shows no Switch, and no `status: downloaded` next to Active. **Download** puts a
preview on the device and **Switch** restarts into it. Deleting the preview that runs goes back to the
default bundle first.

**Incompatible** lists downloads made for another native build in one grouped card, with their title,
branch, environment, who published them and when, and size. They can't run here. **Delete all**
removes them.

### Theme

`theme` takes one of three things:

- **Nothing.** The built-in light or dark theme, following the device. These are the only two built in.
- **A partial theme, by hand.** Any of the [theme keys](/docs/preview/reference#theme). The rest come
  from light or dark.
- **An expo-devtools palette.** The same colours object your app gives
  [`@axonpack/expo-devtools`](/docs/expo-devtools/themes), so the two look alike. It is told apart by
  its `textPrimary` and `accent` keys and mapped by `fromDevtoolsPalette`. This package does not
  depend on expo-devtools.

```tsx
// By hand
<PreviewList theme={{ mode: 'dark', primary: '#16a34a', radius: 8, fonts: { bold: 'Inter-Bold' } }} />

// The palette your app gives expo-devtools, typed as its `Palette`
<PreviewList theme={brandPalette} />
```

`LIGHT_THEME` and `DARK_THEME` are exported to build on. Every key and its defaults are on
[Reference](/docs/preview/reference#theme).

### Labels

Change any text with `labels`:

```tsx
<PreviewList labels={{ backToDefault: 'Back to the store build', previewsTitle: 'QA builds' }} />
```

`status`, `statusShort` and `timeAgo` are merged per key, so `labels={{ statusShort: { broken:
'Crashed' } }}` changes only that one. Some labels are deprecated: `title`, `base`, `stopServer`,
`stopDevPreviewServer` and `localSuffix` are no longer shown, `backToBase` is used only when
`backToDefault` is not set, and `status` still shows for any status `statusShort` does not set. Every
label and its default is on [Reference](/docs/preview/reference#labels). `DEFAULT_LABELS` is exported.

### Layout and your own content

`PreviewList` is a FlatList, so it takes FlatList's props too. By default the end of the list leaves
room for a floating tab bar; set your own with `contentContainerStyle`. Add your own content above
the header card with `ListHeaderComponent`, or after the last row with `ListFooterComponent`:

```tsx
<PreviewList
  style={{ flex: 1 }}
  contentContainerStyle={{ paddingBottom: 140 }}
  ListFooterComponent={<Text style={{ textAlign: 'center' }}>Build 1.4.0 (212)</Text>}
/>
```

Every prop, and the few the list keeps for itself, are on
[Reference](/docs/preview/reference#previewlist-props).

## Show the list anywhere

`PreviewList` is an ordinary React Native component. It brings no navigation and no screen of its
own, so put it wherever QA can reach it: its own screen, a tab, a stack screen, a `Modal`, a bottom
sheet, a hidden debug screen, or behind a shake or a long press.

What it needs:

- **The provider above it.** Without one it throws `usePreview needs a <PreviewProvider> above it.`
  A provider at the root covers every screen and modal. If a bottom sheet or portal library renders
  its content somewhere else in the tree, that place has to be inside the provider too.
- **A bounded height.** It is a FlatList, so give it `style={{ flex: 1 }}` inside a parent that has
  a height: a screen, or a view with `flex: 1`. Never put it inside a vertical `ScrollView`. Nested
  lists warn and stop virtualizing. Add your own content with `ListHeaderComponent` and
  `ListFooterComponent` instead.
- **Your own way to open and close it.** There is no ready-made modal, and `usePreview()` has no show
  or hide. The screen, tab or modal that holds the list decides when it shows.

It can be mounted in more than one place at once, and mounted and unmounted as often as you like.
Its state lives in module stores, so every copy shows the same list. Opening it does not ask the
bucket again: the provider did that at start, and a pull down or **Refresh** asks again. Dev preview
servers are looked for only while a list is mounted, and the search stops when the last one
unmounts.

The list does not hide itself when `enabled` is false, so hiding the tab, button or gesture that
opens it in store builds is the app's job. `usePreview().enabled` tells you when.

To show only what runs, such as a strip on every screen, you don't need the list. See
[Show the status anywhere](#show-the-status-anywhere).

### A screen with expo-router

```tsx
// app/previews.tsx
import { PreviewList } from '@axonpack/preview';

export default function PreviewsScreen() {
  return <PreviewList style={{ flex: 1 }} />;
}
```

Open it from a settings row or a debug menu with `router.push('/previews')`.

### A modal

The app keeps the open state. The close button is the list's own `ListHeaderComponent`, above the
header card:

```tsx
import { PreviewList, usePreview } from '@axonpack/preview';
import { useState } from 'react';
import { Button, Modal } from 'react-native';
import { SafeAreaView } from 'react-native-safe-area-context';

export function PreviewsButton() {
  const { enabled } = usePreview();
  const [open, setOpen] = useState(false);
  if (!enabled) return null;
  return (
    <>
      <Button title="Previews" onPress={() => setOpen(true)} />
      <Modal visible={open} animationType="slide" onRequestClose={() => setOpen(false)}>
        <SafeAreaView style={{ flex: 1 }}>
          <PreviewList
            style={{ flex: 1 }}
            ListHeaderComponent={<Button title="Close" onPress={() => setOpen(false)} />}
          />
        </SafeAreaView>
      </Modal>
    </>
  );
}
```

A bottom sheet, a shake or a gesture works the same way: whatever opens it sets `open`.

### A tab with a floating tab bar

By default the end of the list leaves room for iOS 26's floating tab bar. For a tab bar of your own
that floats over the content, set `paddingBottom` to fit it:

```tsx
// app/(tabs)/previews.tsx
import { PreviewList } from '@axonpack/preview';

export default function PreviewsTab() {
  // Your tab bar's height, the space under it, and a gap.
  return <PreviewList style={{ flex: 1 }} contentContainerStyle={{ paddingBottom: 120 }} />;
}
```

## Your own screen

`usePreview()` gives the same data and actions. It needs the provider above it.

```tsx
import { usePreview } from '@axonpack/preview';
import { Button, FlatList, Text, View } from 'react-native';

export function MyPreviews() {
  const preview = usePreview();
  if (!preview.enabled) return null;
  return (
    <FlatList
      data={preview.items}
      refreshing={preview.loading}
      onRefresh={preview.refresh}
      keyExtractor={(item) => item.id}
      renderItem={({ item }) => (
        <View>
          <Text>{item.entry.title} ({item.status})</Text>
          <Button title="Switch" onPress={() => preview.switchTo(item.id)} />
        </View>
      )}
      ListFooterComponent={<Button title="Use the default bundle" onPress={() => preview.switchTo(null)} />}
    />
  );
}
```

The fields and actions are on [Reference](/docs/preview/reference#usepreview).

## Show the status anywhere

So QA always knows what they are looking at, and how to get back. `usePreviewStatus()` returns what
the list's header card shows, so a banner, a badge or a debug screen of your own says the same thing
the list does. It needs the provider above it.

```tsx
import { usePreviewStatus } from '@axonpack/preview';
import { Button, Text, View } from 'react-native';

export function BundleBanner() {
  const status = usePreviewStatus();
  if (status.isDefault) return null;
  return (
    <View style={{ backgroundColor: '#1d4ed8', padding: 8 }}>
      <Text style={{ color: 'white' }}>{status.label}</Text>
      {status.environment ? <Text style={{ color: 'white' }}>env: {status.environment}</Text> : null}
      <Button title="Use the default bundle" onPress={status.backToDefault} />
    </View>
  );
}
```

`status.label` is one sentence, such as "Preview, Login fix" or "Expo server, localhost:8081". Render
the banner inside the provider, above your navigation. The example app shows one on every tab. Pass
the same `labels` as the list (`usePreviewStatus(labels)`) and the kind names match.

Every field and action is on [Reference](/docs/preview/reference#usepreviewstatus).

`useRunning()` still works, and returns what `status.running` holds. The default bundle is now
`kind: 'default'`, with `source` saying where it comes from. 0.1.0 said `kind: 'base'`.
